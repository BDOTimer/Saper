0. КРАТКИЙ СПИСОК ФИЧ
--------------------------------------------------------------------------------
- Синглтон ComputerBrain с безопасным reset() между партиями.
- Синхронное планирование одного хода ИИ без движения армий.
- Четыре профиля (Барон, Джокер, Рыцарь, Король) с разными весами,
  порогами, радиусом угрозы и приоритетами производства.
- Фильтрация живых армий, resetTurn() и сортировка юнитов внутри армий.
- Сбор обстановки: свои/нейтральные/вражеские/руинные города и вражеские
  армии по клеткам с суммарной силой.
- Оценка угроз своим городам по гарнизону, силе врага и defenseRatio.
- Управление производством: профильные приоритеты, seeded-выбор Джокера,
  самый быстрый тип для угрожаемого города, запрет сброса активного слота.
- Проверка ёмкости производства по лимитам игрока: общие лимиты армий и
  юнитов, а также отдельные лимиты армий с 1/2/3 юнитами.
- Ожидание производства при исчерпанных лимитах без создания лишних армий.
- Оборона угрожаемых городов с проверкой достаточности сил и осторожностью
  Барона.
- Наступление по нейтральным/вражеским городам, вражеским армиям и руинам.
- Проверка odds и порога attackOdds перед атакой.
- Запрет ухода последнего гарнизона из осаждённого города.
- Забор монстров из руин только неполной армией и только без кулдауна/врага.
- Fallback для освобождения города с 4 полными армиями.
- Поиск пути A* с блокировками, резервированием целей и обходом своих армий.
- Проверка и повторное использование сохранённых маршрутов.
- Детерминированный «рандом» на mulberry32/hash2 без Math.random.
- Строгие сортировки кандидатов и целей для воспроизводимости.
- Сводка плана { playerIndex, armies, routes, defended, production, limits }.
- Получение лимитов из Judge либо их самостоятельный расчёт при одиночном
  вызове; лимиты записываются в player.limits.
- Отсутствие DOM/Three.js/async/звука и импортов вне core.
- Интеграция с Judge, ArmyMover, BattleView, руинами и производством.


1. НАЗНАЧЕНИЕ
--------------------------------------------------------------------------------
ComputerBrain — планировщик хода для не-человеческих игроков (ИИ).
Он не двигает армии самостоятельно: по итогам планирования он только:
  - назначает армиям army.route (массив клеток) и army.cellGoal;
  - при необходимости меняет тип производства в городах через
    setCityProduction().

Фактическое движение выполняет ArmyMover, бой — BattleView, производство —
production.js/Judge. Модуль синхронный, не использует DOM, Three.js, звук,
async/await, Promise, setTimeout, Math.random.

Импорты только из core:
  - AiBrainHelper (поиск пути);
  - STATE (world/turn по умолчанию);
  - mulberry32, hash2 (детерминированный «рандом»);
  - productionOptions, productionTurns, setCityProduction;
  - MAX_ARMIES_PER_CITY, MAX_ARMY_SIZE;
  - canCreateArmy, canGrowArmy, computeGameLimits (core/g-limits.js);
  - ruinsCooldownLeft.


2. ПУБЛИЧНЫЙ API
--------------------------------------------------------------------------------
Экспортируются:

  AI_PROFILES
    Объект с профилями 0..3 (ключ — player.aiLevel). Сам AI_PROFILES и
    объекты профилей заморожены; вложенные массивы production технически
    остаются обычными массивами.

  class ComputerBrain
    static get()
      Синглтон, аналог HumanBrain.get().

    static reset()
      Очищает внутренние ссылки и уничтожает синглтон.
      Вызывается из Judge при создании/сбросе партии.

    begin(player, opts = {})
      Главный вход. Вызывается Judge.playerGo() для не-человека после
      player.isTurn = true и до onTurnStart(player).

      opts = { world, turn, limits }
        world  по умолчанию STATE.world;
        turn   по умолчанию STATE.turn или 1;
        limits — необязательный объект лимитов игрока. Judge передаёт сюда
                 this.limits.forPlayer(player). Если limits не передан,
                 ComputerBrain сам вызывает computeGameLimits(world,
                 opts.players ?? [player]).
        players — необязательный список игроков для самостоятельного
                  расчёта лимитов; по умолчанию только текущий player.

      Возвращает сводку:
        {
          playerIndex,
          armies,     // число живых армий
          routes,     // число армий с непустым маршрутом
          defended,   // число защищённых городов
          production, // только фактически изменённые города
          limits      // { maxArmies, maxUnits, maxSmallArmies }
                      // активного игрока
        }

      При отсутствии world/player возвращает пустую сводку и ничего не делает;
      в такой пустой сводке поля limits нет.

      begin() записывает полученные/рассчитанные лимиты в player.limits,
      чтобы остальные системы могли читать их без повторного расчёта.

      begin() идемпотентен по кэшам: каждый вызов заново собирает обстановку,
      стоимости путей и заявки. Ссылки на объекты прошлой партии не хранятся.

4. ПОРЯДОК РАБОТЫ BEGIN
--------------------------------------------------------------------------------
Шаг 1. Контекст.
  world  = opts.world ?? STATE.world
  turn   = opts.turn ?? STATE.turn ?? 1
  profile = AI_PROFILES[player.aiLevel] ?? AI_PROFILES[2]
  limits = opts.limits
           ?? computeGameLimits(world, opts.players ?? [player])
  player.limits = limits

Шаг 2. Живые армии.
  Берутся только армии с alive !== false, у которых есть хотя бы один
  живой юнит. Для каждой армии:
    army.resetTurn();
    army.sortByStrength(true);   // слабые впереди, сильные сзади
  Сам массив player.army не сортируется.

Шаг 3. Сбор обстановки.
  Города делятся на свои, нейтральные, вражеские и руины.
  Строится карта enemyByCell: клетка -> { cell, armies[], power }.

Шаг 4. Стоимости путей.
  Для каждой своей армии один раз вызывается:
    AiBrainHelper.search(world, army)
  Результат кэшируется в ctx.costs (Map army -> { costs, start }).

Шаг 5. Оценка угроз для своих городов.

Шаг 6. Производство (может изменить city.production).
  Перед сменой типа проверяется ёмкость города по лимитам игрока:
  _canProduceInCity() (см. раздел 6.1).

Шаг 7. Оборона (назначает защитников и резервирует их цели).

Шаг 8. Наступление (все армии, кроме назначенных в оборону).

Шаг 9. Fallback (армии без маршрута, застрявшие в переполненных городах).

Шаг 10. Подсчёт сводки.

Приоритет: производство -> оборона -> наступление -> fallback.
Оборона получает армии и цели раньше наступления.


5. СБОР ОБСТАНОВКИ
--------------------------------------------------------------------------------
Города:
  - свои:      ownerId === player.index, type !== 'ruins';
  - нейтральные: ownerId == null, type !== 'ruins';
  - вражеские: ownerId != null && ownerId !== player.index, type !== 'ruins';
  - руины:     type === 'ruins'.

Все четыре списка сортируются детерминированно:
  x ASC, затем y ASC, затем name ASC.

Вражеские армии:
  Один проход по world.cells. В клетке собираются все живые армии,
  у которых idOwner !== player.index. Суммируется totalStrength.
  В enemyByCell попадают только клетки хотя бы с одной такой армией.
  Армии третьих сторон тоже считаются вражескими.

Города на клетке определяются через cell.city (индекс в world.cities)
или world.getCityAt(x, y).


6. ПРОИЗВОДСТВО
--------------------------------------------------------------------------------
Обрабатываются только свои города, для которых productionOptions(city)
непустой.

Смена типа производства разрешена, если:
  - city.production == null; или
  - city.productionOwner !== player.index; или
  - текущий тип больше не входит в productionOptions(city); или
  - city.productionTurnsLeft === city.productionTurnsTotal (слот свободен).

Если производство уже идёт (left < total, владелец совпадает, тип допустим),
тип НЕ сбрасывается и НЕ меняется.

Выбор нового типа:
  1) Если город под угрозой и слот свободен — самый быстрый вариант
     (минимум productionTurns; при равенстве — первый в options).
  2) Если профиль seededProduction (Джокер):
       - options сортируются по productionTurns, затем по исходному индексу;
       - берутся первые два (или меньше);
       - выбор через mulberry32 с seed города (salt 0x50524f44).
  3) Иначе — первый доступный тип из profile.production[city.type].
  4) Если порядок профиля пуст или ни один тип не доступен — options[0].

setCityProduction(city, desired) вызывается только если desired отличается
от city.production и только при разрешённой смене. В сводку production
попадают только успешно изменённые города:
  { city: name, x, y, type }.

Если в городе уже 4 полные армии, производство фактически ждёт освобождения
слота; ComputerBrain не создаёт пятую армию и не меняет тип производства.
Если хотя бы одна из четырёх армий ещё может принять юнита, смена типа
разрешена (см. 6.1). Фактический спавн выполняет production.js/Judge.


6.1. ЛИМИТЫ ИГРОКА
--------------------------------------------------------------------------------
ComputerBrain не создаёт армии и юнитов сам: он только выбирает производство.
Поэтому лимиты проверяются до смены типа производства, а окончательное
разрешение на спавн всё равно выдаёт production.js/Judge.

Источник лимитов:
  Judge создаёт GameLimits(world, activePlayers), обновляет его перед ходом
  игрока и перед производством и записывает результат в player.limits.
  В begin() Judge передаёт opts.limits = judge.limits.forPlayer(player).
  Если begin() вызван отдельно, ComputerBrain сам строит лимиты через
  computeGameLimits(world, opts.players ?? [player]).

  Объект лимитов содержит:
    maxArmies;
    maxUnits;
    maxSmallArmies = { 1, 2, 3 };
    служебные поля mapWidth, mapHeight, mapArea, totalCities, playerCount,
    citiesPerPlayer и playerIndex.

  maxUnits — общий лимит всех живых юнитов игрока (включая героев), а не
  только новых. Он действует с начала партии; стартовая армия из 11 юнитов
  ниже минимума 80.

Формула (core/g-limits.js):
  totalCities   = число городов с type !== 'ruins' (нейтральные входят);
  playerCount   = число активных игроков, минимум 1;
  citiesPerPlayer = max(1, ceil(totalCities / playerCount));
  mapSpan       = sqrt(width * height);
  maxArmies     = clamp(citiesPerPlayer + ceil(mapSpan / 12), 8, 40);
  maxUnits      = clamp(citiesPerPlayer * 8 + ceil(2 * mapSpan), 80, 320);
  maxSmallArmies[1] = clamp(ceil(maxArmies * 0.40), 1, 16);
  maxSmallArmies[2] = clamp(ceil(maxArmies * 0.25), 1, 10);
  maxSmallArmies[3] = clamp(ceil(maxArmies * 0.15), 1,  6).

  Константы формулы собраны в LIMIT_POLICY. totalCities считается по
  фактическому списку городов мира, поэтому сгенерированные крепости и
  захолустья могут поднять лимиты выше базовой конфигурации.

  Примеры:
    40x40, 40 городов, 2 игрока -> 24 армии, 240 юнитов,
    малые армии { 1: 10, 2: 6, 3: 4 }.
    40x40, 42 фактических города, 2 игрока -> 25 армий, 248 юнитов,
    малые армии { 1: 10, 2: 7, 3: 4 }.

Что проверяет ComputerBrain:
  _planProduction() вызывает _canProduceInCity(city) до выбора типа.
  _canProduceInCity():
    1) limits отсутствуют -> производство разрешено;
    2) клетки города нет -> производство запрещено;
    3) собираются свои живые армии в клетке города;
    4) если хотя бы одна армия может принять юнита по canGrowArmy() —
       производство разрешено;
    5) если своих живых армий в городе уже >= MAX_ARMIES_PER_CITY (4) —
       производство запрещено;
    6) иначе производство разрешено только при canCreateArmy().

  canCreateArmy() проверяет:
    - общее число живых армий игрока < maxArmies;
    - общее число живых юнитов игрока < maxUnits;
    - число живых армий размера 1 < maxSmallArmies[1].

  canGrowArmy() проверяет:
    - в армии меньше MAX_ARMY_SIZE юнитов;
    - общее число живых юнитов игрока < maxUnits;
    - для неживой/пустой армии — общий лимит армий;
    - если после добавления армия станет размера 1, 2 или 3, соответствующий
      maxSmallArmies[размер] ещё не исчерпан.
  Для армий размера 4 и больше отдельных лимитов нет: действуют только
  maxArmies, maxUnits и MAX_ARMY_SIZE.

Поведение при исчерпании:
  - если _canProduceInCity() вернул false, ComputerBrain не меняет
    production в этом городе; уже начатое производство не сбрасывается;
  - бот не создаёт армию и не добавляет юнита в обход лимита: фактический
    spawn повторно проверяет те же лимиты в production.js/Judge;
  - при реальном спавне production.js сначала пытается добавить юнита в
    подходящую существующую армию (крупные армии имеют приоритет), и только
    затем создаёт новую; ComputerBrain этот выбор не дублирует;
  - при заполненном лимите производство ждёт освобождения ёмкости; при
    следующей проверке counts пересчитываются по текущим армиям;
  - на выбор маршрута, оборону и наступление лимиты напрямую не влияют:
    они ограничивают только количество армий/юнитов и размеры малых армий;
  - специального слияния малых армий для обхода лимита нет: бот использует
    существующую армию, если canGrowArmy() разрешает её рост;
  - fallback сам по себе освобождает город только при 4 полных армиях;
    если производство ждёт из-за общего maxArmies/maxUnits, отдельного
    манёвра «освободить ёмкость» нет;
  - изменение чисел в LIMIT_POLICY (core/g-limits.js) автоматически меняет
    расчёт и для ComputerBrain, и для production.js: дублирующих констант
    в планировщике нет.


7. ОЦЕНКА УГРОЗ
--------------------------------------------------------------------------------
Для каждого своего города:
  garrisonPower — сумма totalStrength своих живых армий в клетке города.
  threatPower — максимум power среди вражеских клеток, для которых
                манхэттенское расстояние до города <= profile.threatRadius.
  threatCell — клетка самой сильной угрозы; используется для перехвата.
  threatened = threatPower > 0
               && garrisonPower < threatPower * profile.defenseRatio.

Город с врагом внутри клетки тоже считается угрожаемым (threatPower > 0).
Если клетки города нет — запись создаётся с нулями и threatened = false.
Ценность города: capital 120, fortress 70, provincial 50, backwater 30,
неизвестный тип 50.


8. ОБОРОНА
--------------------------------------------------------------------------------
Угрожаемые свои города сортируются:
  ценность DESC, затем координаты/имя.

Для каждого города:
  threshold = threatPower * defenseRatio.
  Кандидаты — все живые армии, которые:
    - ещё не назначены в оборону;
    - не стоят в самом защищаемом городе;
    - могут покинуть текущий город (_canReleaseFromCity);
    - имеют конечную стоимость пути до города;
    - для перехвата — конечную стоимость пути до threatCell.

Проверка _canReleaseFromCity:
  - армия не в городе -> можно;
  - город не свой -> можно;
  - город является целью обороны -> нельзя (гарнизон уже там);
  - город не под угрозой и без врага -> можно;
  - иначе можно, только если в городе >= 2 своих живых армий.
  То есть последняя армия осаждённого города не уходит.

Если профиль defenseCautious (Барон) и среди кандидатов нет ни одного
достаточно сильного (power >= threshold) — город пропускается.

Сортировка кандидатов:
  - sufficient (power >= threshold) идут первыми;
  - среди sufficient: turns ASC, power DESC, army.id ASC;
  - среди insufficient: power DESC, turns ASC, army.id ASC.

Перехват угрозы:
  - если threatCell известен и не совпадает с городом;
  - кандидат имеет конечный interceptCost;
  - odds = power / (power + threatPower) >= profile.attackOdds.
  Перехватчики сортируются: interceptTurns ASC, power DESC, army.id ASC.
  Выбирается первый, для которого построен маршрут до threatCell.
  Это позволяет сильной армии уничтожить угрозу, а не метаться между
  крепостью и своим городом.

Если перехват невозможен — выбирается первый кандидат с маршрутом до города.
Армия получает route/cellGoal, помечается assigned, цель резервируется,
defended++.
Один защитник на город; один город на армию.

После назначения армии выставляется aiGuardCity = город. Пока в городе
сохраняется threatPower > 0, армия-гарнизон не уходит на обычные цели:
  - _guardThreat() возвращает запись города, если армия стоит в нём;
  - в _planAttack разрешена только цель threatCell (сортировка на угрозу);
  - когда threatPower становится 0, aiGuardCity сбрасывается, и армия
    снова может наступать.


9. НАСТУПЛЕНИЕ
--------------------------------------------------------------------------------
Доступные армии — все живые, кроме назначенных в оборону.
Сортировка: totalStrength DESC, army.id ASC.

Для каждой армии:
  1) Hold-guard: если армия — последний гарнизон своего города и город
     под угрозой/содержит врага, маршрут очищается и армия пропускается.
     Проверка: _canReleaseFromCity(army, threats, null).
  2) Если у армии есть aiGuardCity и она стоит в этом городе при
     threatPower > 0, разрешена только цель threatCell; иначе маршрут
     очищается и армия остаётся в гарнизоне (_guardThreat).
  3) Если сохранённый маршрут валиден (_validSavedRoute) — он сохраняется,
     цель резервируется, новая цель не ищется.
  4) Иначе route/cellGoal очищаются и ищется новая цель.

Кандидаты целей:
  - нейтральные города;
  - вражеские города;
  - вражеские армии;
  - руины.
Исключаются: своя клетка, уже зарезервированные цели, дубликаты.
Вражеская армия в чужом городе не добавляется отдельно — город уже
добавлен как enemy-city. Вражеская армия в своём городе добавляется
как enemy-army.

Руины добавляются только если:
  - армия не заполнена (army.isFull === false);
  - руины не на кулдауне (ruinsCooldownLeft === 0);
  - в клетке руин нет вражеской армии.

Стоимость и вероятность:
  cost = стоимость пути до клетки (должна быть конечной);
  turns = max(1, ceil(cost / max(1, army.movePoints)));
  enemyPower = суммарная сила врагов в целевой клетке;
  myPower = totalStrength армии;
  odds = myPower / (myPower + enemyPower), если enemyPower > 0, иначе 1.

Для всех целей, кроме руин, при enemyPower > 0:
  если odds < profile.attackOdds — цель отбрасывается.

Формулы score:
  neutral-city:
    cityValue * neutralWeight / (1 + turns)
  enemy-city:
    cityValue * enemyCityWeight * oddsFactor / (1 + turns)
    oddsFactor = enemyPower > 0 ? (0.5 + odds) : 1.5
  enemy-army:
    ((15 + enemyPower * 1.5) * huntWeight + threatBonus) / (1 + turns)
    threatBonus = максимум по своим городам, где threatPower > 0 и
      клетка врага в пределах threatRadius:
      cityValue * defenseWeight
  ruins:
    25 * ruinsWeight / (1 + turns)

Если profile.risk > 0, score умножается на:
  1 + risk * hash2(cell.x, cell.y, seedForArmy(army, 0x4a495454))
где hash2 возвращает число 0..1. Это детерминированный jitter.

Сортировка целей:
  score DESC -> turns ASC -> y ASC -> x ASC -> type ASC.

Если profile.topN > 1 (Джокер topN = 2):
  - выбирается случайный индекс среди topN через mulberry32 с seed армии
    (salt 0x544f504e);
  - выбранный кандидат ставится первым, остальные сохраняют порядок.
  - если путь к выбранному кандидату не построился, перебираются остальные.

Первый успешный маршрут назначается армии, цель резервируется.
Маршрут может проходить через незащищённый чужой/нейтральный город и
попутно захватить его — это поведение ArmyMover/Cell, не запрещено.


10. FALLBACK (ОСВОБОЖДЕНИЕ ПЕРЕПОЛНЕННЫХ ГОРОДОВ)
--------------------------------------------------------------------------------
Fallback нужен, когда в городе 4 полные армии и производство не может
создать юнита, а сама армия осталась без маршрута.

Кандидаты — армии, не назначенные в оборону и без маршрута.
Сортировка: army.id ASC.

Условия для исходного города:
  - армия стоит в своём городе;
  - город не под угрозой;
  - в клетке нет врага;
  - в городе >= MAX_ARMIES_PER_CITY (4) своих живых армий;
  - все эти армии заполнены (isFull === true);
  - из этого города в текущем плане ещё не уводили армию (freedCities).

Цели:
  - свои или нейтральные города, кроме исходного;
  - цель не зарезервирована;
  - в цели нет вражеской армии;
  - стоимость пути конечна.

Сортировка целей: cost ASC, turns ASC, координаты/имя города.
Первый город с построенным маршрутом выбирается; цель резервируется;
исходный город помечается freedCities; moved++ (внутренний счётчик,
в сводку не входит).

Особенности:
  - из одного города уходит только одна армия за ход;
  - fallback не проверяет, есть ли в целевой городе свободный слот
    производства, поэтому может отправить армию в уже полный город;
  - fallback не проверяет odds — цель должна быть без врага, поэтому
    бой не планируется.


11. МАРШРУТЫ, БЛОКИРОВКИ, A*
--------------------------------------------------------------------------------
Стоимости путей:
  Для каждой армии один раз выполняется AiBrainHelper.search(world, army).
  Это A* без конкретной цели, результат — карта costs.

Построение маршрута (_routeToGoal):
  1) Сначала пробует восстановить путь из уже посчитанных costs:
     AiBrainHelper.pathFrom(costs, start, goal).
  2) Путь принимается, если он непустой и не проходит через заблокированные
     клетки (кроме самой цели).
  3) Иначе строится новый маршрут:
     AiBrainHelper.buildRoute(world, army, goal, { blockCells }).

Заблокированные клетки (_blockCells):
  - свои живые армии вне городов (кроме самой планируемой армии);
  - вражеские армии во всех клетках, кроме выбранной цели;
  - цели, уже зарезервированные другими армиями (кроме выбранной цели).
  Свои города не блокируются: в них можно входить.
  Цель всегда разрешена, даже если она попала в blocked-набор.

Маршрут — массив клеток без стартовой клетки, последняя клетка = goal.
Соседство — манхэттенское, ровно 1 клетка.

Стоимость шага:
  - дорога (cell.hasRoad) или город (cell.city >= 0) -> 1;
  - иначе cell.staminaCost;
  - если стоимость не конечна -> Infinity (непроходимо).
A* дополнительно учитывает минимальный запас хода юнитов армии, поэтому
шаг дороже minMove не попадает в маршрут.

Маршрут не двигает армию. Движение выполняет ArmyMover по шагам, тратя
moveLeft и останавливаясь перед своими армиями вне городов.


12. ПРОВЕРКА СОХРАНЁННЫХ МАРШРУТОВ
--------------------------------------------------------------------------------
_validSavedRoute(army, threats, reserved) требует:
  - route — непустой массив, cellGoal задан;
  - последняя клетка маршрута строго равна cellGoal;
  - цель всё ещё валидна (_goalStillValid);
  - стартовая клетка существует;
  - каждая клетка маршрута существует в мире и является тем же объектом;
  - расстояние между соседними клетками ровно 1;
  - ни одна клетка не зарезервирована;
  - первый шаг по стоимости <= army.movePoints;
  - все промежуточные клетки (кроме цели) не содержат свою армию вне города
    и не содержат вражескую армию.

Проверка цели (_goalStillValid):
  - руины:
      армия не заполнена, кулдаун 0, в клетке нет врага;
  - свой город:
      город под угрозой ИЛИ в клетке есть враг;
  - нейтральный город:
      цель валидна (ownerId == null);
  - вражеский город:
      ownerId !== player.index (в том числе город третьей стороны);
  - не город:
      в клетке есть вражеская армия.

Если маршрут валиден, он сохраняется и цель резервируется. Если нет —
маршрут очищается и армия ищет новую цель.

Особенность: тип цели не сохраняется в армии. Поэтому маршрут, созданный
к нейтральному городу, который стал вражеским, может остаться валидным
как enemy-city; и наоборот. Это осознанное упрощение.


13. ДЕТЕРМИНИЗМ
--------------------------------------------------------------------------------
В модуле нет Math.random(), async/await, Promise, setTimeout,
requestAnimationFrame, DOM, Three.js, звука и рендера.

Случайность только через:
  - mulberry32(seed) — число 0..1;
  - hash2(x, y, seed) — число 0..1.

Seed базы:
  worldSeed = world.seed (или 0)
  turn = текущий ход
  playerIndex = player.index
  base = worldSeed
         ^ imul(turn + 1, 0x9e3779b1)
         ^ imul(playerIndex + 1, 0x85ebca6b)
         ^ imul(salt, 0xc2b2ae35)
  (все операции с >>> 0)

Seed армии:
  base(salt) ^ imul((army.id ?? 0) + 1, 0x27d4eb2d)

Seed города:
  base(salt)
  ^ imul((city.x ?? 0) + 1, 0x27d4eb2d)
  ^ imul((city.y ?? 0) + 1, 0x165667b1)

Соли:
  0x50524f44 — seeded-производство Джокера;
  0x4a495454 — jitter риска;
  0x544f504e — выбор из topN.

Детерминированность обеспечивается также явными сортировками:
  - города: x, y, name;
  - армии: id;
  - цели: score, turns, y, x, type;
  - защитники: sufficient, turns/power, id.

При одинаковом состоянии мира, ходе, игроке и армиях план одинаков.
Бой в core/g-battle.js по-прежнему использует Math.random — это вне
ответственности ComputerBrain.


14. ТРЕБОВАНИЯ К ОБЪЕКТАМ
--------------------------------------------------------------------------------
world:
  - cities или cityList.list;
  - cells — массив клеток;
  - get(x, y);
  - getCityAt(x, y) (опционально);
  - seed.

player:
  - index;
  - aiLevel;
  - army[];
  - limits (опционально; ComputerBrain записывает сюда активные лимиты).

army:
  - id, x, y;
  - units[] с флагом alive;
  - alive;
  - totalStrength;
  - movePoints;
  - isFull;
  - resetTurn();
  - sortByStrength(true);
  - route, cellGoal (записываются планировщиком).

city:
  - name, x, y, type, ownerId;
  - production, productionOwner,
    productionTurnsLeft, productionTurnsTotal.

limits (если передан или рассчитан):
  - maxArmies;
  - maxUnits;
  - maxSmallArmies с ключами 1, 2, 3.

ComputerBrain не изменяет world, кроме:
  - city.production и связанных полей через setCityProduction();
  - army.route / army.cellGoal;
  - army.resetTurn() / sortByStrength().
Остальные данные только читаются, включая ruinsCooldownLeft().


15. ИНТЕГРАЦИЯ С ИГРОЙ
--------------------------------------------------------------------------------
Judge.playerGo():
  для не-человека после player.isTurn = true и до onTurnStart(player)
  вызывает ComputerBrain.get().begin(player, {
    world,
    turn,
    limits: this.limits.forPlayer(player),
  }).
  Перед этим Judge._refreshPlayerLimits() обновляет GameLimits и
  player.limits; перед производством в _doCities() обновление повторяется.

Game._onTurnStart():
  строит routeView (маршруты ИИ не рисуются), затем
  mover.enqueue(player.army.slice()).

ArmyMover:
  выполняет шаги по маршрутам, тратя moveLeft; останавливается перед
  своими армиями вне городов; при нехватке очков сохраняет маршрут.

RouteView:
  рисует только маршруты человека; маршруты ИИ не отображаются.

Бой:
  ArmyMover.pauseForBattle() / resumeAfterBattle();
  Game._onBattleRequest() ставит паузу до BattleView.runBattle();
  BattleView.onClose возобновляет движение;
  при закрытии force пауза не снимается (сценарий destroy/restart).

Руины:
  при посещении руин ИИ сразу получает монстров через
  Game._claimRuinsMonsters(); человек — после закрытия townView.

Производство:
  Judge/Game тикает производство; ComputerBrain только выбирает тип
  и не спавнит юнитов. При выборе типа он учитывает лимиты через
  _canProduceInCity(); фактический spawn повторно проверяет лимиты
  в spawnProducedUnit()/tickCityProduction().

17. ОГРАНИЧЕНИЯ И ОСОБЕННОСТИ
--------------------------------------------------------------------------------
1) Перехват и guard — эвристика: при нескольких угрозах выбирается
   сильнейшая, остальные обрабатываются на следующих ходах.
2) Fallback может выбрать целевой город без свободного слота производства
   и без проверки числа армий в нём.
3) _planDefense при недоступном пути у sufficient-кандидата может выбрать
   insufficient-кандидата (сначала перебираются все кандидаты по порядку).
4) Тип цели сохранённого маршрута не хранится, поэтому neutral-city,
   ставший enemy-city, может остаться валидным; см. раздел 12.
5) _planProduction не меняет тип производства, если _canProduceInCity()
   запрещает его: при 4 полных армиях, исчерпанном maxArmies/maxUnits
   или лимите армии следующего размера производство ждёт. Пятая армия
   не создаётся.
6) Внутренний счётчик moved в fallback в сводку не попадает.
7) Game.destroy не вызывает ComputerBrain.reset(); статический reset()
   доступен для ручного сброса (например, при рестарте/тестах).
8) Маршрут ИИ может проходить через незащищённый чужой/нейтральный город
   и захватить его попутно.
9) Враги третьих сторон учитываются как враги наравне с основным
   противником.
10) Планировщик не хранит состояние между ходами, кроме того, что уже
    записано в армии и города: route, cellGoal, production.
11) ComputerBrain не создаёт армии и юнитов сам и не обходит лимиты:
    окончательный spawn выполняет production.js/Judge.
12) Отдельного слияния малых армий для освобождения лимита нет; бот растит
    уже существующую армию, если canGrowArmy() это разрешает.
13) Лимиты не ограничивают перемещение армий напрямую: они проверяются при
    производстве и при получении монстров из руин. Общее число юнитов от
    перемещения не меняется.
14) Ручной обмен юнитами через ArmyChangeView пока не проверяет
    maxSmallArmies; это вне зоны ответственности ComputerBrain.

20. ПРИМЕРЫ ПОВЕДЕНИЯ БОТОВ
--------------------------------------------------------------------------------
Ниже описано только то, что можно увидеть в партии и проверить повторным
запуском. Бот заменяет игрока-человека в решениях о производстве, обороне
и наступлении, но не ведёт переговоров и не заключает союзов.

Если сказано «при прочих равных», имеются в виду одинаковые расстояние,
ценность цели, силы армий и отсутствие более выгодного варианта.

20.1. Общие привычки всех ботов
--------------------------------------------------------------------------------
- Сначала бот выделяет защитников для угроз своим городам, и только
  потом использует оставшиеся армии для наступления.
- Бот не отменяет уже начатое им производство. Если слот занят, он ждёт.
- Если слот свободен и лимиты позволяют, бот выбирает тип по своему
  профилю. Если город под угрозой и слот свободен, все боты сначала строят
  самый быстрый вариант.
- Если в городе уже четыре армии, исчерпан общий лимит армий/юнитов или
  лимит армии следующего размера, новое производство ждёт освобождения
  ёмкости; лишняя армия или юнит не появляются.
- Последняя армия не уходит из города, который уже под угрозой или в
  котором стоит враг. Если в городе две и более своих армий, одна может
  уйти. В спокойном городе бот может увести и последнюю армию.
- На один угрожаемый город бот выделяет не больше одного защитника (если
  подходящий есть). Две армии не идут защищать один и тот же город в
  одном плане.
- Разные армии не получают одну и ту же цель в одном плане.
- Бот не проходит сквозь свою армию вне города и сквозь вражескую армию,
  если её клетка не выбрана целью. Такие клетки он обходит. Свои города
  сами по себе путь не блокируют.
- Сохранённый маршрут продолжается, пока цель остаётся подходящей и путь
  свободен. Если цель стала невалидной или путь перекрыли, бот выбирает
  новую цель.
- Против защищённой цели бот атакует только при достаточной доле своей
  силы. Против пустого города или руин этот порог не мешает.
- В руины бот идёт только неполной армией, не на кулдауне и только если
  там нет врага. Полная армия руины игнорирует.
- Если в городе четыре полные армии и ни одна не получила цель, одна
  армия уходит в ближайший свой или нейтральный город без врага. Из
  одного города за ход уходит только одна такая армия. Если город под
  угрозой или в нём есть враг, этот манёвр не выполняется.
- Бот может попутно занять незащищённый чужой город, через который
  проходит его маршрут.
- При одинаковом состоянии мира и одинаковом ходе план бота повторяется.
  Исход боя может отличаться: боевой бросок находится вне плана ИИ.

20.2. БАРОН — осторожная игра
--------------------------------------------------------------------------------
Как выглядит игра за Барона:
  Он расширяется в нейтральные города, строит тяжёлые войска и редко
  тратит их на охоту за армиями. При невыгодном соотношении сил не
  атакует.

Что можно проверить:
  - Атакует защищённую цель только при доле своей силы не ниже 68%.
    При 60 против 40 — не атакует. При 68 против 32 — может атаковать.
  - Из нейтрального и вражеского города при прочих равных выбирает
    нейтральный. При равной цене и расстоянии даже незащищённый
    вражеский город для него менее привлекателен, чем для остальных.
  - Он реже всех выбирает охоту за армиями: при сопоставимой выгоде чаще
    идёт в город или руины, а не в погоню за армией.
  - Руины у него в самом низу приоритетов: при равном расстоянии и
    доступности он предпочтёт город. В руины пойдёт только неполной
    армией и только если нет более выгодной доступной цели.
  - Замечает врагов далеко: радиус тревоги 8 клеток. Считает город
    угрожаемым, если гарнизон слабее 90% силы самой сильной вражеской
    группировки в этом радиусе. Например, при враге силой 100 и гарнизоне
    80 он уже поднимает тревогу (если враг не стоит в самом городе).
  - Если ни один кандидат не набирает 90% силы угрозы, подкрепление не
    отправляет. Город остаётся с тем, что есть. Это его главное отличие
    от остальных ботов.
  - Если достаточно сильный защитник есть и путь к нему свободен,
    посылает одну армию; из тревожного города последнюю армию не
    забирает.
  - Производство тяжёлое: в столице сначала тяжёлая пехота, затем
    тяжёлая конница, маги, драконы; в крепости — тяжёлая пехота,
    арбалетчики, катапульты, тяжёлая конница; в провинции — средняя
    пехота, лучники, лёгкая пехота, лёгкая конница; в глухом городе —
    лучники, лёгкая пехота, лёгкая конница.
  - Не случайничает: при одинаковой обстановке повторяет тот же выбор
    цели.

20.3. РЫЦАРЬ — сбалансированная игра
--------------------------------------------------------------------------------
Как выглядит игра за Рыцаря:
  Он развивает нейтральные города, но не отказывается от вражеской цели,
  если перевес достаточный. Защищает города, но не так осторожно, как
  Барон.

Что можно проверить:
  - Атакует защищённую цель при доле своей силы не ниже 60%.
    При 60 против 40 — может атаковать. При 50 на 50 — нет.
  - Нейтральные города для него чуть ценнее вражеских, но незащищённый
    вражеский город получает полуторный бонус. Поэтому при равной
    ценности и расстоянии он может выбрать вражеский город, а не
    нейтральный.
  - Радиус тревоги 7 клеток. Считает город угрожаемым, если гарнизон
    слабее 85% силы врага. При враге силой 100 и гарнизоне 80 — уже
    тревога (если враг не в самом городе).
  - Не осторожничает при защите: если достаточно сильного защитника нет,
    всё равно посылает сильнейшего из доступных. Город может получить
    подкрепление, которого не хватит для победы.
  - Охотится за армиями умеренно: при прочих равных чаще Барона, реже
    Джокера и Короля.
  - Руины ценит средне: при прочих равных выше Барона, ниже Джокера и
    Короля.
  - Производство сбалансированное: в столице сначала тяжёлая конница,
    затем тяжёлая пехота, маги, драконы; в крепости — тяжёлая пехота,
    арбалетчики, тяжёлая конница, катапульты; в провинции — средняя
    пехота, лёгкая конница, лучники, лёгкая пехота; в глухом городе —
    лёгкая конница, лучники, лёгкая пехота.
  - Имеет небольшую повторяемую поправку к оценке целей (до 10%).
    Из-за неё может измениться порядок близких по оценке целей, но при
    повторении той же обстановки выбор повторится.

20.4. ДЖОКЕР — риск и импровизация
--------------------------------------------------------------------------------
Как выглядит игра за Джокера:
  Он идёт на почти равные бои заметно чаще Барона и Рыцаря, уступая в
  этом только Королю. При прочих равных он охотится за армиями сильнее
  Барона и Рыцаря, а руины ценит выше всех. Его можно узнать по выбору
  из двух лучших целей и производству без фиксированного порядка.

Что можно проверить:
  - Атакует защищённую цель при доле своей силы не ниже 52%.
    При 52 против 48 — может атаковать. При 50 на 50 — нет.
  - Радиус тревоги 6 клеток. Считает город угрожаемым, если гарнизон
    слабее 75% силы врага. При враге силой 100 и гарнизоне 80 тревоги
    ещё нет (если враг не в самом городе).
  - Не осторожничает при защите: посылает сильнейшего из доступных, даже
    если его не хватит для победы.
  - Сам по себе он не отдаёт предпочтения нейтральному или вражескому
    городу; вражеский город получает обычный бонус за слабость гарнизона.
    При прочих равных он охотится за армиями сильнее Барона и Рыцаря, но
    слабее Короля; руины при прочих равных ценит больше всех.
  - Из двух лучших целей выбирает одну «случайно» (на самом деле по
    внутреннему зерну). Поэтому может пропустить самую выгодную цель и
    пойти во вторую по выгоде.
  - Получает повторяемую надбавку к оценке целей до 25%. Это сильнее
    всего меняет его приоритеты среди ботов.
  - Производство без фиксированного порядка: когда слот свободен, он
    выбирает один из двух самых быстрых доступных вариантов (или
    единственный, если вариант один). Если город под угрозой и слот
    свободен, всё равно сначала выбирает самый быстрый вариант.
  - Его «случайность» воспроизводима: при том же состоянии мира и том
    же ходе он повторит выбор.

20.5. КОРОЛЬ — агрессивная игра
--------------------------------------------------------------------------------
Как выглядит игра за Короля:
  При прочих равных он чаще других выбирает вражеские города и армии, а
  нейтральные города и дальние угрозы для него менее важны. Это самый
  агрессивный из четырёх ботов.

Что можно проверить:
  - Атакует защищённую цель при доле своей силы не ниже 48%.
    При 48 против 52 — может атаковать. При 50 на 50 — тоже может.
  - При прочих равных выбирает вражеский город охотнее нейтрального.
    Незащищённый вражеский город для него особенно привлекателен.
  - Радиус тревоги всего 5 клеток. Считает город угрожаемым, если
    гарнизон слабее 70% силы врага. При враге силой 100 и гарнизоне 80
    тревоги нет. Врага дальше 5 клеток он может вообще не учитывать при
    обороне.
  - Не осторожничает при защите: посылает сильнейшего из доступных, даже
    если его не хватит для победы.
  - При прочих равных сильнее всех охотится за вражескими армиями.
    Руины по приоритету ниже только Джокера.
  - Производство тяжёлое и агрессивное: в столице сначала драконы, затем
    тяжёлая конница, маги, тяжёлая пехота; в крепости — катапульты,
    тяжёлая конница, тяжёлая пехота, арбалетчики; в провинции — средняя
    пехота, лёгкая конница, лёгкая пехота, лучники; в глухом городе —
    лёгкая конница, лучники, лёгкая пехота.
  - Имеет повторяемую надбавку к оценке целей до 15%.
  - Даже при агрессии не уводит последнюю армию из города, который уже
    под угрозой или содержит врага. Правило «последний гарнизон остаётся»
    действует для всех ботов.

--------------------------------------------------------------------------------

Радиус тревоги, клеток            8       7        6        5

Что означают строки таблицы:
  - «Порог доли силы» — минимальная доля своей силы в сумме сил своих и
    вражеских войск, при которой бот готов атаковать защищённую цель.
  - «Радиус тревоги» — на каком расстоянии бот вообще замечает вражеские
    армии для обороны города.
  - «Тревога, если гарнизон меньше» — сравнение гарнизона с силой самой
    сильной вражеской группировки в радиусе.
  - «Вес» — относительная важность цели при выборе. Чем выше, тем чаще
    бот выбирает такую цель при прочих равных.
  - «Защита при нехватке сил» — что бот делает, если не может послать
    защитника, который по силе не уступает угрозе. Барон не посылает
    никого, остальные посылают сильнейшего из доступных.
    У Барона строка «не идёт» означает: среди кандидатов нет достаточно
    сильного. Если сильный кандидат есть, но путь к нему перекрыт,
    возможен редкий выбор более слабого защитника.
  - «Производство» — общий стиль. Точные первые типы по городам указаны
    в описаниях профилей.

Лимиты одинаковы для всех четырёх ботов и не зависят от профиля: каждый
бот получает maxArmies/maxUnits/maxSmallArmies своего игрока. Профиль
влияет только на выбор типа производства, пока ёмкость не исчерпана.

20.7. Короткие сценарии для проверки
--------------------------------------------------------------------------------
Сценарий «равный бой»: у бота 50 силы, у защитника 50.
  Порог атаки проходит только Король. Барон, Рыцарь и Джокер эту цель
  не выбирают.

Сценарий «заметный перевес»: у бота 60 силы, у защитника 40.
  Порог атаки проходят Рыцарь, Джокер и Король; Барон — нет.

Сценарий «сильный перевес»: у бота 68 силы, у защитника 32.
  Порог атаки проходят все четыре бота.

Сценарий «враг рядом с городом»: враг силой 100 в радиусе, гарнизон 80,
врага в самом городе нет.
  Барон и Рыцарь считают город угрожаемым, Джокер и Король — нет.
  Если есть свободная армия, Барон пришлёт помощь только при достаточно
  сильном защитнике; Рыцарь, Джокер и Король пришлют сильнейшего из
  доступных, даже если его мало.

Сценарий «выбор между нейтральным и пустым вражеским городом»:
  при равной цене и расстоянии Барон выберет нейтральный, а Рыцарь,
  Джокер и Король могут выбрать вражеский из-за полуторного бонуса за
  отсутствие гарнизона.

Сценарий «город с четырьмя полными армиями»: город не под угрозой,
врага в нём нет, ни одна армия ещё не получила цель.
  Все боты могут вывести одну армию в ближайший свой или нейтральный
  город без врага. Вторую армию из этого же города в том же плане они
  не выводят.

20.8. Кого может заменить бот
--------------------------------------------------------------------------------
Барон подходит на роль осторожного игрока: он развивает нейтральные
города, редко охотится за армиями и атакует защищённую цель только при
заметном перевесе. Если достаточно сильного защитника нет, он может
оставить город без помощи.

Рыцарь подходит на роль универсального игрока: он не отказывается от
вражеской цели при достаточном перевесе, защищает города и готов
послать даже слабое подкрепление, если сильного нет.

Джокер подходит на роль рискованного игрока: он принимает почти равные
бои, выше всех ценит руины и может выбрать вторую по выгоде цель.

Король подходит на роль агрессора: при прочих равных он предпочитает
вражеские города и армии, а угрозы замечает только в пределах 5 клеток.
