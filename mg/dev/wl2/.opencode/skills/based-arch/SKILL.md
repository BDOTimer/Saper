# Архитектура пошаговой стратегии (JS + Three.js)

## Когда использовать

- Добавление или изменение логики ходов, юнитов, боя, экономики
- Работа с состоянием игры (сохранение, загрузка, откат)
- Любые изменения в Three.js сцене (рендеринг юнитов, карты, эффектов)
- Рефакторинг существующего кода проекта
- Пользователь говорит "проверь архитектуру" или "почему это плохо"

## Жёсткие правила (нарушение = провал)

### 1. Логика ходов НЕ ЗАВИСИТ от Three.js
Игровая логика (состояние юнитов, ресурсы, карта, правила ходов) должна быть в отдельных модулях без единого `import * as THREE`. Three.js — только для отображения. Если видишь `THREE.Vector3` в файле с логикой боя — это ошибка, исправляй.

### 2. Детерминизм обязателен
Пошаговая стратегия должна воспроизводиться. Любой `Math.random()` в логике ходов — красный флаг. Если нужен рандом (например, крит), используй seeded PRNG с явным seed, сохраняемым в состоянии игры. Агент НЕ ДОЛЖЕН использовать `Math.random()` без явного согласования с пользователем.

### 3. Состояние игры — единый источник правды
Запрещено хранить "истинное" состояние в объектах Three.js (`mesh.userData.hp = 10`). Состояние живёт в отдельном хранилище (plain object или класс `GameState`). Three.js меши только **читают** его при рендере. Если видишь изменение геймплейных данных через `mesh.userData` — переписывай.

### 4. Утечки памяти Three.js недопустимы
При удалении юнита, тайла или эффекта агент ОБЯЗАН вызвать `dispose()` для geometry, material и texture. Проверяй каждый `scene.remove()` на наличие соответствующего `dispose()`. Это самая частая причина деградации FPS в долгих сессиях.

### 5. Никакого `requestAnimationFrame` для логики ходов
Игровой цикл для пошаговой игры — это **событийный** цикл (ход игрока → валидация → изменение состояния → рендер). `requestAnimationFrame` допустим только для анимаций и рендеринга, но не для "тикания" логики.

### 6. Разделяй слои

```
src/
├── core/           # Чистая логика: юниты, карта, бой, экономика (без DOM, без THREE)
├── state/          # Хранилище состояния + сериализация
├── render/         # Three.js: сцена, меши, материалы, анимации
├── input/          # Обработка кликов/клавиш → команды для core
└── ui/             # HTML/Canvas UI (ресурсы, панели, диалоги)
```

Правило: `core/` **никогда** не импортирует из `render/` или `ui/`. `render/` может читать из `state/`, но не менять логику.

## Gotchas (типичные ошибки, которые агент допускает)

- **`mesh.userData.hp`**: агент обожает хранить HP юнита прямо на меше. Это ломает сериализацию и детерминизм. Проверяй и исправляй.
- **`Math.random()` в бою**: агент добавит рандомный урон "для интереса". Требуй seeded PRNG.
- **`scene.add()` без `dispose()`**: при смерти юнита меш удаляется, но geometry/material остаются в памяти. Всегда добавляй cleanup.
- **Логика хода в обработчике клика**: `onClick` → `mesh.position.x += 1` — это ошибка. Клик должен создавать команду (`MoveUnitCommand`), которая проходит валидацию в `core/` и только потом обновляет состояние, после чего `render/` синхронизируется.
- **`new THREE.Vector3()` в цикле каждый кадр**: агент может создать тысячи векторов в `animate()`. Переиспользуй временные объекты.

## Чеклист перед завершением изменений

Прежде чем сказать "готово", проверь:

- [ ] В файлах `core/` и `state/` нет импорта `three`
- [ ] Нет `Math.random()` без seeded PRNG в логике
- [ ] Каждый `scene.remove()` сопровождается `dispose()` для geometry/material/texture
- [ ] Состояние игры не хранится в `mesh.userData` (кроме чисто визуальных флагов)
- [ ] Логика ходов не привязана к `requestAnimationFrame`
- [ ] Новые юниты/объекты имеют уникальные ID в состоянии, а не ссылки на меши
